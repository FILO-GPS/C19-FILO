# Ambiente e convenzioni tecniche

## Installazione
Node 22 LTS >=22.14.0, npm 10, Git, PostgreSQL 16 (Docker facoltativo), Chromium. Installare dalla root con `npm ci`. Modificare i manifest e rigenerare il lockfile con `npm install` soltanto per aggiornamenti approvati, poi verificare `npm audit` e tutti i controlli pertinenti. Non usare `npm audit fix --force`. Non eseguire installazioni indipendenti nelle sottocartelle. npm Workspaces gestisce frontend, backend ed extension; le dipendenze si dichiarano nel workspace che le usa.

## Versioni e decisioni di compatibilità
Next.js e `eslint-config-next` 16.4.6, Vitest e Coverage V8 5.1.2, Prisma CLI e client 7.10.1. Le major sono state aggiornate rispetto alle specifiche iniziali per correggere gli advisory rilevati durante il bootstrap. Mantenere ESLint 9.39.5: pur essendo deprecato, è compatibile con i peer range dei plugin effettivamente risolti, diversamente da ESLint 10. Riesaminare il vincolo in un task dedicato quando l'intero insieme dei plugin supporterà una versione mantenuta. L'override root `@prisma/config` → `effect: 3.22.1` corregge GHSA-7589-6fvf-x4pw; mantenere il lockfile verificato e rivalutare l'override quando Prisma adotta una versione corretta. Non modificare l'override o le major senza approvazione e verifica. Zero advisory nell'audit non costituisce una garanzia assoluta di sicurezza. Vite 6.4.6 è condiviso tra la root della monorepo e il workspace extension, garantendo la compatibilità tra CRXJS, Vitest e la Browser Extension. Mantenere allineate le versioni di Vite per evitare incompatibilità tra i tipi dei plugin. Eventuali aggiornamenti devono essere approvati e validati mediante type-check, build e test.

 `concurrently` coordina due processi locali, non introduce un orchestratore di agenti. Il mapping SDD resta Vercel/Render; il backend è un secondo progetto Next.js con soli Route Handlers.

## Ambiente
Copiare i template nei file locali, senza versionarli. Su PowerShell:
```powershell
Copy-Item frontend/.env.example frontend/.env.local
Copy-Item backend/.env.example backend/.env
Copy-Item extension/.env.example extension/.env.local
Copy-Item .env.test.example .env.test
```
I valori di esempio del database sono esclusivamente per sviluppo locale con Docker. Usare password locali proprie se necessario. Impostare un JWT secret locale quando la funzionalità di sessione viene realizzata. La chiave Gemini personale di Cline non è la chiave di FILO. Il Gateway resta in mock per verifiche automatiche; eventuale modalità live soltanto backend, con dati sintetici, autorizzazione e condizioni del provider verificate. Non usare utenti scolastici reali.

Avviare PostgreSQL con `docker compose up -d` oppure creare `filo_dev` e `filo_test` su una propria istanza PostgreSQL. L'istanza compose è limitata a localhost e crea due database al primo avvio. Non usare database di produzione. `npm run test:integration` carica `.env.test` se presente; in CI le variabili sono iniettate dal workflow. Il test di infrastruttura controlla una connessione al DB di test con Prisma CLI. Prima di implementare persistenza, assegnare un unico task per schema Prisma e migrazioni, mappando i modelli approvati; validare con `npm exec -w backend -- prisma validate --config prisma.config.ts`, applicare le migrazioni di sviluppo con `npm run db:migrate` (solo filo_dev) e generare esplicitamente il client con `npm run db:generate`; aggiungere seed e isolamento test. Prisma 7 non genera il client o avvia il seed automaticamente durante le migrazioni. Lo schema iniziale contiene solo datasource/generator; non contiene entità inventate. `db:generate` richiede modelli effettivi. Lo schema usa il generatore `prisma-client` con output `backend/src/generated/prisma/`, escluso da Git, ESLint e Prettier. La CLI legge la URL da `backend/prisma.config.ts`; gli script caricano esplicitamente `backend/.env` o `.env.test` rispettivamente per sviluppo e test. Le variabili di processo hanno precedenza: non riutilizzare una shell con DATABASE_URL di un ambiente diverso. Nel task condiviso di persistenza installare `@prisma/adapter-pg` della versione compatibile con Prisma 7.10.1 e `pg` nel backend, verificare nuovamente audit e lockfile, e inizializzare PrismaClient dal percorso generato con il driver adapter. Non usare il vecchio import da `@prisma/client` per il client generato. Per il database test, applicare migrazioni con `npm run db:deploy:test` (wrapper di `prisma migrate deploy`) usando esplicitamente la connessione test, non `migrate dev`; verificare sempre il nome del DB prima di operazioni distruttive. La CI valida lo schema e genera il client/applica le migrazioni se esistono file di migrazione SQL; ogni PR con persistenza deve aggiungere migrazioni e test reali. Il seed di dominio e la pulizia tra test saranno implementati con lo schema condiviso.

## Comandi
`npm run dev` avvia frontend :3000 e backend :3001 insieme; `npm run dev:ext` avvia Vite/CRXJS separatamente. `npm run build` compila tutti e tre; gli script individuali sono indicati nel README. Verificare `http://localhost:3001/api/health` e la pagina frontend. L'extension scaffold non intercetta prompt e non richiede permessi sui siti: i TM implementeranno il flusso previsto nel RAD con i permessi minimi.

## Testing e CI
Vitest: `tests/unit/` con mock; `tests/integration/` con DB isolato. `npm test` non usa il database. `npm run test:integration` richiede `filo_test` e forza modalità mock. Gli smoke test iniziali verificano endpoint tecnico e connessione; non sono test dei requisiti né sostituiscono i frame. Per i nuovi test isolare i dati, non usare rete Gemini/SMTP, non alterare attesi per far passare i test. Quando le migrazioni/seed esistono, aggiornare la preparazione dei test e usare fixture/cleanup tra i test. Playwright è opzionale; i test manuali dell'estensione sono documentati nel task/PR.

## Deploy
Frontend su Vercel (root `frontend`); backend su Render (workspace `backend`, build `npm run build:backend`, start `npm run start:backend`, porta `PORT` fornita dall'hosting). Per entrambi installare dalla root del monorepo/lockfile; quando sono presenti i modelli, il deploy backend deve generare il client prima della build e applicare le migrazioni approvate con un passaggio di rilascio separato (non con gli script locali); configurare il build del provider per usare il workspace corretto, senza duplicare lockfile. Configurare URL di backend, autorizzazioni cross-origin/cookie e HTTPS secondo i contratti concordati; la chiave Gemini, JWT e DB rimangono lato server. Non deployare lo scaffold come se fosse FILO completo.
